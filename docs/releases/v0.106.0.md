# v0.106.0 — Signatures that cover what they claim, verified Evidence Bundles, a trusted maker-checker, real PII crypto-shred, and batch jobs that no longer inherit your shell

**Released 2026-10-22.** A security release for the evidence chain. Each fix below closes a
gap where a signature, a root or a check covered less than it appeared to: the NovaSeal signing
intent, file names in the capsule Merkle root, the tree size in NovaSeal log roots, the
signatures and `manifest_hash` of an Evidence Bundle, the "exact" verdict of a re-performance
attestation, the identity behind a maker-checker signature, and the environment SLURM and LSF
copy into a job. It also makes `nova pii erase` a real crypto-shred for capsules captured with
`--pii-subject` (experimental), and extends mocked replay to Google ADK and OpenAI Agents SDK
tools (experimental). **This release changes behaviour in several places. Read
[Behaviour changes and upgrade notes](#behaviour-changes-and-upgrade-notes) before upgrading.**

Maturity labels follow the project convention: **works today**, **experimental**, **planned**,
**future design**. Each feature is labelled in the [CHANGELOG](../../CHANGELOG.md) entry for this
version; experimental features below stay experimental.

## What's in it

### Security and evidence integrity

| Area | What changed |
|---|---|
| **Signing intent is signed (ADR-0309)** | The FDA 21 CFR §11.50 intent (authored, reviewed, approved, …) was a label beside the DSSE signature, outside the signed bytes. It is now bound into the sealed payload (`_novaseal.signing_intent`). `nova verify` reports `signing_intent_status: signed` only when the signed copy agrees with the label; an edited label fails. Seals made before this release report `label-only` and no intent. |
| **Capsule Merkle root commits to file names (ADR-0310)** | The RFC 6962-shaped root over a capsule hashed contents only, so a rename that kept the sort order left the root — and every bundle subject, consent attestation, AI-BOM and baseline pin built on it — unchanged. New roots use a v2 leaf that also commits to each file's relative path, under its own domain byte, so accepting old v1 roots cannot be turned into a downgrade. Roots recorded earlier still verify, and a renamed capsule never satisfies a v2 root. Comment and annotation subjects stay on v1 so existing comments stay attached. |
| **NovaSeal log roots are versioned (ADR-0313)** | The original (v1) root duplicated the last node of an odd level, so `[a, b, c]` and `[a, b, c, c]` had the same root. New logs write v2 (RFC 9162 Merkle Tree Hash and proofs). A root is always compared together with its tree size; `nova verify` with the sealer's log rejects an altered `tree_size`, and a witness no longer cosigns a checkpoint whose size the consistency proof does not establish. Existing v1 logs and seals verify unchanged. |
| **`nova verify <bundle>.zip` runs the whole recipe** | It used to recompute artifact digests only, so a bundle whose attestation had been edited — with the new digest written back into `manifest.json` — verified as PASSED. It now recomputes `manifest_hash`, verifies every attestation's DSSE signature (and its detached `.sig`), checks each statement's subject against the manifest, and recomputes the run subject from the bundle's own `run-capsule/` copy (and the lineage subject from `edges.jsonl`), because `manifest.json` itself is not signed. An edited or added capsule file fails even when every digest has been rewritten. The key ships inside the bundle, so `--public-key` now pins the signer; without it the output says `signer not pinned`. Hostile or malformed input is reported, never raised on. |
| **`attest-replay --mode exact` refuses what it cannot vouch for** | Exact mode re-executes nothing. An ineligible or unassessed run is now refused (`NotAttestableError`, exit 1) and nothing is signed, instead of being attested `match: exact`. |
| **Promote signatures need a trust root (ADR-0315)** | A promote envelope was verified against the certificate it carried, so the names the policy matched were whatever the signer put in a self-signed certificate; any key could sign a bypass; a bypass's expiry came from an unsigned file; and a signed policy was never verified. Every proposal, approval, signed policy and bypass signer must now chain to a pinned CA (`--ca-bundle` or `NOVAFABRIC_PROMOTE_CA_BUNDLE`, offline RFC 5280 validation shared with NovaSeal). A bypass counts only when signed by an approver in the latest policy, for this capsule, and unexpired by its **signed** `valid_until`. |
| **Registry maker-checker binds keys to identities (ADR-0312)** | `nova promote propose` / `approve` signatures are verified against an operator-held trust list (`NOVAFABRIC_PROMOTE_SIGNERS` or `$NOVAFABRIC_HOME/promote-signers.yaml`), and separation of duties compares the bound identities. New `nova promote keygen --identity NAME`. `nova promote direct` into `production` needs an explicit `promote_direct` policy allow. |
| **SLURM and LSF jobs run with a minimal environment (ADR-0311)** | The job script was already filtered (ADR-0270), but `sbatch` and `bsub` copy their own environment into the job by default, so jobs ran with the user's whole shell. Both now run with the scheduler client's variables, login basics such as `PATH`/`HOME`/`USER` and the POSIX `LC_*` names, `NOVAFABRIC_*` and `extra_env` only; so do `scontrol`, `sacct`, `bjobs` and `bkill`. Confirmed on SLURM 23.11.4 and on Volclava 2.2 (an OpenLava-family LSF): before the fix a planted secret reached the job, after it it did not, and `extra_env` delivered the named variable. |
| **No off-host runner forwards a NovaFabric credential** | The `NOVAFABRIC_*` prefix capture needs inside a job also matched credentials such as `NOVAFABRIC_SERVER_TOKEN`, `NOVAFABRIC_API_KEY` and `NOVAFABRIC_POSTGRES_DSN`, so `docker`, `kubernetes`, `slurm` and `lsf` carried them into the job (SLURM also onto `sbatch`'s command line). Credential-shaped `NOVAFABRIC_*` names are no longer forwarded; `extra_env` still sends one deliberately. |
| **`nova verify` names the signer that verified** | `signer_subject` came from `signatures[0]` even when that entry did not verify, so a junk first entry could show someone else's certificate subject. It now describes the signature that verified. |
| **Every write-permitting replay flag is policy-gated** | `--allow-external-side-effects` and `--allow-unknown-mutation` now go through the audited `replay_mutating` policy, as `--allow-mutating` already did. A deny or a policy-engine error refuses the replay before anything runs. |
| **A destroyed DEK no longer survives in `dek.db-wal`** | `DEKStore` sets `secure_delete` and truncates the WAL after an erasure. |

### Privacy

- **Per-subject PII encryption at capture (ADR-0314, experimental).** `nova capture
  --pii-subject <id>` (needs `NOVA_PII_PEPPER`) replaces detected PII and literal occurrences of
  the subject id with AES-256-GCM envelope tokens under that subject's DEK. After `nova pii
  erase <id>` the tokens cannot be opened; readers render `[erased]`, and a modified token
  renders `[tampered]`. If the DEK is unavailable, the PII is masked, never stored in plaintext,
  and the workload is not blocked. Not covered: binary or oversize artifacts, media blobs and
  in-process capsules. Erasure documentation now says that erasure makes PII unreadable **only**
  in capsules captured this way, and a guard test keeps that claim tied to the code.

### Replay (experimental, ADR-0306 slices 3 and 4)

- **Google ADK tools.** `novafabric.adapters.google_adk.make_tool_plugin()` records each ADK
  tool call under `nova capture python …`, and mocked replay returns the recorded result through
  ADK's documented `before_tool_callback` short-circuit, so the tool body never runs.
- **OpenAI Agents SDK function tools.** `novafabric.adapters.openai_agents.wrap_tools([...])`
  does the same for `FunctionTool`s. It replaces `on_invoke_tool`, an undocumented seam checked
  against `openai-agents` 0.17.x; an SDK release can break it.
- **Nested `record.tool` boundaries** are served, with the records written inside them consumed
  as *covered*. **MCP arguments** are matched after secret redaction. A report-only
  **tool-result echo check** compares the tool results a request sends back with the recorded
  ones.

### Docs and packaging

- **The PyPI page's README links work.** A build hook rewrites relative links and images to
  absolute, version-pinned GitHub URLs in the published long description.
- **The container eval suites** (GAIA, AgentBench, MMLU, SWE-bench, TruthfulQA) no longer carry
  a placeholder image and fail with an error naming the unset variable (ADR-0308).
- Architecture, CLI reference, security policy and decisions index are updated for every change
  above.

## Behaviour changes and upgrade notes

Each item below is flagged as a behaviour change in the [CHANGELOG](../../CHANGELOG.md).

1. **SLURM and LSF jobs no longer see your shell's variables.** A workload that read an API key
   or other variable from the submitting shell must now receive it explicitly:
   `--runner-option extra_env=OPENAI_API_KEY=...`. If you used `--runner slurm` or
   `--runner lsf` on v0.105.0 or earlier, treat any credential that was in that shell as
   readable by the job and rotate it (see [SECURITY.md](../../SECURITY.md)). No off-host runner
   forwards a credential-shaped `NOVAFABRIC_*` variable any more (for example
   `NOVAFABRIC_SERVER_TOKEN` or `NOVAFABRIC_POSTGRES_DSN`); pass one with `extra_env` if a job
   really needs it, and rotate any that were set when you used `docker`, `kubernetes`, `slurm`
   or `lsf`.
2. **`nova seal verify` / `nova seal approve` refuse promote signers until a trust root is
   configured** (exit 3, with a message naming the fix). Pass `--ca-bundle` or set
   `NOVAFABRIC_PROMOTE_CA_BUNDLE`. For local development only, `--insecure-self-signed` /
   `NOVAFABRIC_PROMOTE_INSECURE_SELF_SIGNED=1` accepts self-signed signers. `nova serve`,
   `nova server` and `nova export-model-independence` read the same variables. A bypass signed
   by someone who is not an approver in the latest policy is now ignored.
3. **Registry promotion needs identities and a trust list.** (1) Each signer runs `nova promote
   keygen --identity <name>`. (2) An operator collects the printed entries into the trust list,
   keeping only the roles each person holds. (3) Add `--identity` to every `propose` / `approve`.
   (4) Replace scripted `promote direct --to production` with `propose` + `approve`, or load an
   OPA policy that allows `promote_direct`. Proposals stored earlier read as `unverified` and
   cannot be approved; a new `propose` supersedes them. Exit codes: `3` proposal-side failure,
   `4` approval-side failure, `6` self-approval.
4. **`nova verify <bundle>.zip` may fail where it passed** if an attestation, its signature or
   `manifest_hash` does not check. Bundles exported by `nova export-evidence` verify unchanged.
5. **`nova evidence attest-replay --mode exact` exits 1** for a run that is not exact-eligible,
   and signs nothing.
6. **New capsule roots and NovaSeal log roots use v2.** Releases before v0.106.0 cannot verify
   the carried inclusion proof of a v2 seal (except at power-of-two tree sizes) and report its
   log check as failed; verify v2 seals with v0.106.0 or later. Calling
   `verify_consistency_proof()` now requires `old_size=` and `new_size=`.
7. **Seals made by earlier versions report `signing_intent_status: label-only`** and no intent;
   they are not invalid.
8. **Replays using `--allow-external-side-effects` or `--allow-unknown-mutation` are refused**
   where your policy denies `replay_mutating`.
9. **The container eval suites need both `NOVAFABRIC_<SUITE>_OCI_IMAGE` and
   `NOVAFABRIC_<SUITE>_OCI_DIGEST`.**

Capsules, seals and bundles written by earlier versions validate and verify unchanged. Existing
capsules are not rewritten.

## Try it

```bash
pip install --upgrade "novafabric==0.106.0"
nova --version                         # novafabric 0.106.0

nova export-evidence <run-id> -o bundle.zip
nova verify --public-key signer.pub.pem bundle.zip   # signatures, manifest_hash, subjects, pinned signer

nova verify --json ~/.novafabric/capsules/<run-id>   # signing_intent_status

nova capture --runner slurm --runner-option extra_env=OPENAI_API_KEY=$OPENAI_API_KEY -- python agent.py

NOVA_PII_PEPPER=... nova capture --pii-subject user-42 -- python agent.py
nova pii erase user-42                 # destroys the DEK; --pii-subject tokens then render [erased]
```

## Verification

Release-preparation gates on the release tree: the full release tier (`make test-par`, the
CI `unit` job's command) ran **19,957 passed, 173 skipped**, coverage **93.74 %** (gate 90 %);
its two failures were test fixtures that signed a made-up capsule root, which the stricter
bundle verifier now rejects, and both pass after the fixtures were corrected. `ruff check`
clean; `mypy src` clean (993 files); `uv lock --check` clean; the decisions index, the replay
support matrix, the OpenAPI specs and the architecture diagrams regenerate unchanged.

Every security fix in this release has a test that fails when the fix is removed (checked by
reverting each guard). Before tagging, an independent attack pass rebuilt the original exploits
against the release code through the CLI: the edited signing intent, the renamed capsule, the
exact attestation of an ineligible run, promote verification with no trust root, and the SLURM
/ LSF submit environment (with stand-in `sbatch`, `bsub`, `scontrol`, `sacct` and `bjobs` that
record their environment). The bypass cases of ADR-0315 and the bundle tampering cases are
covered by the test suite. The pass found four further gaps — a v1/v2 capsule-root downgrade,
bundle subjects compared only with the unsigned manifest, NovaFabric credentials forwarded
under the `NOVAFABRIC_*` prefix, and a signer name read from an unverified signature entry —
which are fixed in this release; the downgrade, credential and signer-name attacks were re-run
against the fix, and the bundle case is pinned end to end by `nova verify` tests. The
SLURM and LSF changes were also confirmed on real schedulers (SLURM 23.11.4 and Volclava 2.2,
in disposable VMs). The [CHANGELOG](../../CHANGELOG.md) entry names the tests that pin each
change.
