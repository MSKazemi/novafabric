# v0.14.0 — NovaSeal Linked-Envelope Chain Maker-Checker

**Released:** 2026-05-15
**ADR:** [ADR-0059](../decisions.md)
**Research:** `design/research/novafabric-maker-checker-sod/`

---

## What's new

This release ships the **NovaSeal linked-envelope chain maker-checker** (cap-001 through cap-003 from the maker-checker SoD research study). It adds cryptographic two-person authorization at the **capsule signing level**: two separate DSSE envelopes (Proposal + Approval) are linked via SHA-256 of JCS-canonicalized bytes, making the approval chain independently and offline-verifiable.

This is distinct from the **asset registry maker-checker** (ADR-0058, v0.13.0), which enforces two-actor approval for asset status transitions. The two mechanisms are complementary:

| Mechanism | Object | Binding | Verifiable |
|---|---|---|---|
| `nova promote propose/approve` (ADR-0058) | Asset status in registry | Ed25519 keypair + SQLite row | Registry DB required |
| `nova seal propose/approve/verify` (ADR-0059) | Capsule DSSE envelope | ECDSA P-256 + JCS digest | Offline, from bundles alone |

## New commands

### `nova seal propose`

```bash
nova seal propose <capsule-id> \
  --justification "Model v1.0 validated against held-out eval set; p99 < 200ms." \
  --key proposer.pem \
  --cert proposer_cert.pem
# → Proposal created: <uuid>
```

- Justification must be ≥ 20 characters; shorter values cause exit 1 before signing.
- Builds a `promote/proposal/v1` predicate, validates against JSON Schema, signs with ECDSA P-256.
- Records `policy_version` from the active policy at propose-time.
- Stores the envelope at `{data_dir}/promote/{capsule_id}/proposal/{uuid}.json`.

### `nova seal approve`

```bash
nova seal approve <proposal-uuid> \
  --capsule-id <capsule-id> \
  --key approver.pem \
  --cert approver_cert.pem
# Displays proposal details, prompts for confirmation
# → Approval recorded: <uuid>
```

- Fetches and displays the Proposal (capsule_id, justification, proposer, timestamp).
- Computes `proposal_digest = SHA-256(JCS(proposal_envelope_bytes))` — RFC 8785 canonicalization ensures deterministic output.
- Builds a `promote/approval/v1` predicate, validates, signs, stores.

### `nova seal verify`

```bash
nova seal verify <capsule-id> [--offline]
# → SoD verification passed   (exit 0)
# or: proposer key <subject> not in policy proposer_key_ids (exit 3)
```

Five-check verifier (stops at first failure):

| Check | Failure exit code |
|---|---|
| 1. Proposer cert subject ∈ policy.proposer_key_ids | 3 |
| 2. Approver cert subject ∈ policy.approver_key_ids | 4 |
| 3. `proposal_digest` matches SHA-256(JCS(Proposal envelope)) | 5 |
| 4. approver_subject ≠ proposer_subject | 6 |
| 5. Approval timestamp > Proposal timestamp | 7 |

`--offline` is accepted and fully functional (v0.1 does not make network calls during verify).

### `nova policy sign`

```bash
nova policy sign \
  --key admin.pem \
  --cert admin_cert.pem \
  --proposer-subjects "alice,alice-ci" \
  --approver-subjects "bob,carol" \
  --bypass-valid-hours 24
# → Policy signed and stored: version 1
```

Signs and versions a `promote/policy/v1` document in the Merkle log. The verifier loads the policy version recorded in each Proposal's predicate (not the latest), so policy changes cannot retroactively fail in-flight proposals.

## Try it

```bash
# 1. Install
pip install novafabric==0.14.0

# 2. Sign a policy (admin step — do once)
nova policy sign \
  --key admin.pem --cert admin_cert.pem \
  --proposer-subjects "alice" \
  --approver-subjects "bob"

# 3. Propose (alice)
nova seal propose my-capsule-001 \
  --justification "All eval gates green; ready for staging." \
  --key alice.pem --cert alice_cert.pem

# 4. Approve (bob — different identity)
nova seal approve <proposal-uuid> \
  --capsule-id my-capsule-001 \
  --key bob.pem --cert bob_cert.pem

# 5. Verify (auditor)
nova seal verify my-capsule-001
# SoD verification passed
```

- **Tests:** 70 new tests in `tests/promote/`; 2300 total passing
