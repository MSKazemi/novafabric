# NovaFabric v0.77.0 — 2026-07-25

**Finer-grained lineage — row and transformation provenance, privacy-first.**
ADR-0109's verifiable half ships: two additive lineage facets that record *which
rows* and *which operation* produced an edge, storing only hashes and categories —
never a raw key, cell value, or operation body. `experimental`. Full detail:
`CHANGELOG.md` §[0.77.0].

## Highlights

### Transformation facet (NF-062)

`lineage/_facets_v2.build_transform_facet(operation, op_kind=...)` binds a
content-addressed reference to the operation behind a lineage edge — a
`sha256:` digest plus a coarse `op_kind` (e.g. `sql`, `pandas`, `python`). The
sealed capsule keeps the operation itself; the facet keeps only its digest, so two
runs of the same transform share a digest and a verifier can match them without
ever seeing the code.

### Row facet (NF-061)

`build_row_facet(row_keys)` records which rows influenced an output, by **hash of
the row key** — never the raw key or any cell content. The set is bounded (256
keys); overflow truncates and downgrades confidence to `heuristic`, mirroring the
ADR-0090 column cap.

### The privacy invariant is the point (I-2)

The load-bearing rule is **names/keys/hashes, never values**. The tests feed the
builders secret-bearing inputs (`SELECT ssn FROM patients WHERE name = 'Alice'`,
row keys like `user-42`) and assert none of it appears in the serialized facet —
only digests. Row-level is where the privacy line is sharpest, so the row facet is
opt-in and hash-only.

### Additive and unbreakable to write (I-1/I-3/I-4)

Both facets ride the **existing** `LineageEdge.facets` dict — no `LineageStore`
signature change (I-1). The builders are **fail-open** (I-3): they return a facet
or `None` and never raise, so facet extraction can never break a lineage write
(tested against garbage inputs). Facets round-trip through the existing field
unchanged (I-4).

### Scope, honestly

This is the *verifiable half* — the facet format and its builders. Auto-inferring
these facets from a live run (the capture half), the NF-063 in-memory hot
provenance index, and the NF-064 KuzuDB hot-tier remain future design (later
waves). ADR-0109 was accepted (first slice) under delegated authority.

## Upgrade notes

Additive — new module, no breaking changes, no new dependencies. Existing lineage
edges and facets are unaffected.
