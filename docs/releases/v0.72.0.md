# NovaFabric v0.72.0 — 2026-07-25

**Cloud KMS envelope encryption — the trio is complete.** v0.71.0 shipped the AWS
branch; this release adds Azure Key Vault and GCP Cloud KMS, so ADR-0185's
per-object DEK wrapping now works against all three major clouds. Everything new
is `experimental`. Full detail: `CHANGELOG.md` §[0.72.0].

## Highlights

### `AzureKvWrappingBackend` + `GcpKmsWrappingBackend` (ADR-0185)

`trust/novaseal/signing_backend.py` gains two more `KeyWrappingBackend`
implementations:

- **`AzureKvWrappingBackend`** — wraps the data-encryption key with Azure Key
  Vault `wrap_key` / `unwrap_key` (RSA-OAEP-256 by default). `kek_ref()` →
  `azure-kv:<key-id>`.
- **`GcpKmsWrappingBackend`** — wraps with GCP Cloud KMS `encrypt` / `decrypt`.
  `kek_ref()` → `gcp-kms:<resource-name>`.

Both are accepted by `novafabric.trust.envelope_encryption`, so the plaintext KEK
never leaves the cloud KMS and per-object DEK wrapping now spans AWS, Azure, and
GCP.

### Verified locally, honestly

Each backend takes an **injectable client**. The suite verifies the integration
code path against an in-memory fake that implements the SDK's method contract with
a real AES-GCM round-trip — proving wrap/unwrap symmetry, the wrap-capability
gate, and the full `encrypt_blob` / `decrypt_blob` cycle. This is honest
verification of the integration code; **end-to-end against a live Azure Key Vault
or GCP Cloud KMS still requires real cloud credentials** (unlike the AWS backend,
which moto emulates fully). No new *runtime* dependency — the SDKs are the
existing `[seal-azure]` / `[seal-gcp]` extras.

## Upgrade notes

Additive — no breaking changes. Existing local/mock/AWS envelope encryption is
