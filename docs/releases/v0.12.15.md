# v0.12.15 — NovaSeal TSA Signature Verification

Released: 2026-05-15

`verify_timestamp()` now validates the TSA's CMS digital signature in addition
to the hash-integrity check it already performed.  A forged TSR that contained
a correct `messageImprint` hash but an invalid signature now returns `False`
instead of `True`.

---

## Background

RFC 3161 TimeStampResponses are signed CMS (`PKCS#7 SignedData`) structures.
Until this release, `novafabric.trust.novaseal.timestamp.verify_timestamp()`
only checked that `SHA-256(dsse_bytes)` appeared inside the TSR DER blob.
That check confirms the timestamp was issued for the right content but does
not prove the response came from a legitimate TSA: an attacker who could
predict or intercept the hash could synthesise a structurally valid TSR.

v0.12.15 adds a second check: extract the `SignerInfo.signature` and verify
it against the `SubjectPublicKeyInfo` in the first certificate found in
`SignedData.certificates`.  The signature covers `DER(SET OF Attributes)`
where the signed attributes include `messageDigest = SHA-256(TSTInfo)`.

---

## What is verified in v0.1

1. TSR is valid DER with `PKIStatus` granted (0) or grantedWithMods (1).
2. The `messageImprint` hash in the TSR equals `SHA-256(dsse_bytes)`.
3. The TSA's CMS digital signature over the TSTInfo is cryptographically
   valid, checked against the certificate embedded in the TSR.

## What is deferred to v0.2

- **Trust anchor / chain-of-trust** — whether the TSA certificate chains to a
  recognised root CA requires a configurable trust-store; not yet implemented.
- **Revocation checking** — CRL distribution point and OCSP staple validation.
- **Nonce replay protection** — matching the request nonce to the TSR nonce.

---

## Security

### TSA signature now verified (Seal-1)

**Before:** a TSR with `messageImprint` = `SHA-256(dsse_bytes)` but an
arbitrary or zeroed signature would have been accepted as `timestamp_ok=True`.

**After:** `_verify_tsa_signature()` extracts the ECDSA/RSA signature from
`SignerInfo`, reconstructs the `SET OF Attributes` bytes (replacing the
`[0] IMPLICIT` CMS tag with `0x31` per RFC 5652 §5.4), and calls the
`cryptography` library to verify.  A failed verification returns `False`;
`verify_timestamp()` propagates this as `False`.

**Degrade-safe:** when the TSR has no `TimeStampToken`, the CMS structure uses
an unsupported encoding, or the signature algorithm OID is not yet mapped, a
`DEBUG` log line is emitted and the result falls back to checks 1+2 only.
No existing synthetic/mock TSRs are broken.

## Added

### DER helpers

- `_read_tlv(der, pos)` — reads one ASN.1 TLV at `pos`; supports short-form
  and multi-byte long-form lengths; raises `ValueError` on truncated input.
- `_iter_children(der)` — iterates the first-level TLV children of a raw DER
  body; returns `list[tuple[tag, start, end, value]]`; stops gracefully on
  malformed input.

### CMS extraction chain

- `_parse_signer_info(der)` — walks a CMS `SignerInfo` SEQUENCE and returns
  `(signed_attrs_raw, sig_alg_oid_tlv, signature_bytes)`.
- Internal helpers `_extract_token_raw`, `_extract_signed_data_value`, and
  `_extract_signer_info_value` navigate the ContentInfo → SignedData → SET OF
  SignerInfos chain.

### Signature algorithm OID constants

Six OID byte-string constants cover the algorithms most TSAs use in practice:

| Constant | Algorithm |
|---|---|
| `_OID_SHA256_RSA` | sha256WithRSAEncryption |
| `_OID_SHA384_RSA` | sha384WithRSAEncryption |
| `_OID_SHA512_RSA` | sha512WithRSAEncryption |
| `_OID_SHA256_ECDSA` | ecdsa-with-SHA256 |
| `_OID_SHA384_ECDSA` | ecdsa-with-SHA384 |
| `_OID_SHA512_ECDSA` | ecdsa-with-SHA512 |

## Upgrade notes

No API changes.  `verify_timestamp(tsr_bytes, dsse_bytes)` signature is
unchanged.  The only observable difference is that previously-passing forged
TSRs (correct hash, invalid signature) will now return `False`.  All
legitimate RFC 3161 responses from any TSA using RSA or ECDSA are unaffected.
