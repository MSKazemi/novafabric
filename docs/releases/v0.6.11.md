# v0.6.11 — SlurmRunner: sitecustomize injection (wire-level capture works on compute nodes)

Released: 2026-05-09

Second real bug fix surfaced by live SLURM cluster validation. v0.6.10
proved SlurmRunner submits + polls + reads correctly. v0.6.11 makes
*capture itself* actually fire on compute nodes — until this release,
`model-calls.jsonl` was always empty for SLURM-submitted captures
because SlurmRunner wasn't injecting the sitecustomize hook loader.

## What's new

### `SlurmRunner` materializes `sitecustomize.py` to the capsule directory

The capsule directory is on shared filesystem (NFS in the validated
cluster — any cluster's shared scratch / home works). SlurmRunner
writes the hook-loader text into `<capsule_dir>/sitecustomize.py`
before submitting, then prepends `<capsule_dir>` to `PYTHONPATH` in
the sbatch wrap script. The compute node's Python auto-loads
`sitecustomize` at interpreter startup → NovaFabric hooks install
before the user's workload runs.

Previously the wrap script only exported `NOVAFABRIC_*` + `PATH`.
Without `PYTHONPATH` pointing at a sitecustomize, the workload ran
"bare" on the compute node — no hooks, no records, just stdout/stderr.

### Shared `_sitecustomize` module

Extracted the hook-loader text to `src/novafabric/runners/_sitecustomize.py`
so `LocalRunner` (which materializes it to a temp dir) and
`SlurmRunner` (which materializes it to capsule_dir) use the same
canonical string. No more copy-paste drift; future runners (Kubernetes
once we get to live validation) can just import `HOOK_LOADER`.

### Live e2e validation on the cluster

After the fix, an end-to-end test on the same 3-node Vagrant + libvirt
cluster used for v0.6.10:

```
== End-to-end capture test on SLURM ==
  partition  : debug
  python     : /home/vagrant/novafabric-venv/bin/python

== orchestrator returned ==
  exit_code   : 0

== model-calls.jsonl ==
  1 record(s)
    - gen_ai.system=openai  model=gpt-4o  status=error

PASS: wire-level capture fired on the compute node
```

Before v0.6.11 the same workload produced `model-calls.jsonl: EMPTY`.
After v0.6.11: one captured wire-level record from the httpx call the
workload made on the compute node, classified correctly as
`gen_ai.system=openai`, status=error because the connection to
api.openai.com failed (no API key in the test workload — exactly what
we want to verify wire-level capture works).

### `scripts/live_slurm_capture_e2e.py` — pytest-free e2e harness

Companion to `live_slurm_smoke.py`. Submits a small Python workload
that does one httpx POST, then asserts model-calls.jsonl is populated
with the expected record shape.

Run on any SLURM cluster:

```bash
~/novafabric-venv/bin/python scripts/live_slurm_capture_e2e.py debug
```

## Quality

- **675 tests passing** (+3 from v0.6.10 — `TestSlurmRunnerSitecustomizeInjection`)
- **90% coverage** maintained
- ruff clean, mypy strict clean across 91 source files

The new tests assert the contract the live test was about to break:

- `test_sitecustomize_written_to_capsule_dir` — proves SlurmRunner
  materializes the file with the correct content
- `test_pythonpath_in_wrap_script_includes_capsule_dir` — proves the
  wrap script's PYTHONPATH points at it
- `test_existing_pythonpath_preserved` — if a user passes their own
  PYTHONPATH (e.g. venv site-packages), it's appended after capsule_dir
  not overwritten

## Breaking changes

None for callers. The new file write requires `capsule_dir` to be on
a writable filesystem — which it always is for SLURM (must be shared
FS between submitter and compute node anyway). If the write fails for
any reason, SlurmRunner returns `runner_status="failed_setup"` with a
helpful error message instead of submitting silently and producing
empty records.

## What this release also confirms

The v0.6.x SLURM track now has **two distinct live-validated**
behaviors on a real cluster:

1. **SlurmRunner submits + polls + reads correctly** (v0.6.10)
2. **Captured workloads on compute nodes actually emit records to
   shared-FS capsule** (v0.6.11)

That's most of what a production HPC user needs from this runner.
The remaining ROADMAP item ("validated against at least 2 distinct
SLURM cluster configurations") is now half-done; the second
configuration would be a real production HPC site with slurmdbd.
