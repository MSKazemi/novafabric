# NovaFabric v0.94.0 — 2026-07-30

**Two real bugs caught by refusing to trust mocks, one new CLI daemon, and one honest
"this doesn't work yet" note.** This release closes out a backlog-audit pass: it makes
the cluster-scale lineage write path actually work end-to-end against real KuzuDB
(catching a latent Parquet-COPY bug along the way), adds a NATS-JetStream daemon
entrypoint that didn't exist before, fixes a pgBouncer security test that could never
have failed, and adds a multi-TSA fallback for RFC 3161 timestamping. It also documents,
rather than hides, a real remaining gap: the one live NATS event producer in this repo
doesn't speak the taxonomy either Python consumer expects.

## Highlights

### `nova lineage consume` — a working entrypoint for the NATS lineage consumer

`LineageConsumer.run_from_nats()` (cap-006) was fully implemented and tested against
mocks, but had no way to actually run as a deployable process. `nova lineage consume`
wraps it as a foreground daemon with every tunable exposed as a flag.

```bash
nova lineage consume --nats-url nats://hub.example.com:4222 \
  --kuzu-path /var/lib/novafabric/lineage.kuzu
```

Along the way, `bulk_insert_edges()` — the KuzuDB write path — was verified against a
*real* KuzuDB instance for the first time (every prior test mocked the connection). That
caught a real, previously-invisible bug: KuzuDB rejects the `header=true` COPY option
for Parquet sources (it's CSV-only). Fixed, and the write path now does a two-phase COPY
(`LineageNode` then `LineageEdge`) so a KuzuDB `REL TABLE` COPY has valid FROM/TO
references — see [ADR-0219](../decisions.md).

The SCALE-ADR-002 write-throughput benchmark is measured for the first time against
real KuzuDB: **it passes at batch sizes ≥ ~2,000 edges/call (13K–28K edges/s) and falls
short below that (4K–7K edges/s)** — published in `bench/lineage/MEASURED_CEILING.md`.
`run_from_nats()` now buffers edges and flushes on a size-or-time trigger
(`--flush-batch-size 2000` / `--flush-interval-s 15` by default, matching that benchmark).

### Multi-TSA fallback for RFC 3161 timestamping (REG-ADR-007)

`novaseal.yaml` gains an optional `tsa_urls` ordered fallback list — a single
unreachable TSA no longer has to block sealing:

```yaml
tsa_urls:
  - https://tsa.your-qtsp.example/tsr
  - https://freetsa.org/tsr
```

Defaults to `[tsa_url]` when omitted, so existing single-TSA configs are unaffected.
See `docs/novaseal-configuration.md` §1.1.

### `nova doctor --check-scheduler` (PAR-ADR-003 OQ-06)

Detects a scheduler (Slurm, torchrun, OpenMPI, Ray, K8s Job) via its own native env
vars and cross-references the `NOVAFABRIC_*` capture-identity contract. For Slurm,
reads `SLURM_EXPORT_ENV` to tell a site `--export=NONE` policy apart from a
submission-script gap — a fail-loud, on-demand diagnostic that doesn't change
`nova capture`'s existing fail-open default.

### A real security-test fix: the pgBouncer mutant-leak test could never fail

`test_mutant_baseline_leaks_pgbouncer` was supposed to prove the cross-tenant-isolation
mutant baseline actually leaks under pgBouncer transaction pooling. It couldn't —
`BrokenMetadataStore.begin_tenant_context` always re-`SET`s its own correct tenant as
the first statement of every transaction, so neither existing failure signal could ever
fire regardless of pooling config. Fixed the pgBouncer image/config (a `server_reset_query
= DISCARD ALL` default was silently wiping session state between clients) and added a
third "peek without setting" signal that actually detects the real failure mode.

### Consumer-side dedup now survives redelivery across batches (SCALE-ADR-001)

`LineageConsumer.run_once()`'s dedup previously reset on every call — a message
redelivered in a *later* NATS fetch (JetStream's normal at-least-once behavior) was
never caught. Dedup now persists in a bounded, FIFO-evicting cache scoped to the
consumer's lifetime.

### Known limitation, stated honestly: no producer speaks the right taxonomy yet

Wiring up `nova lineage consume` end-to-end surfaced that no code in this repository
publishes events to NATS in a format either Python consumer recognizes. The one real
producer — a Go HPC leaf-node forwarder — uses a different `event_type` taxonomy than
the canonical Python `CapsuleEventType` enum both `LineageConsumer` and the KG ingestion
pipeline expect. Running the real forwarder against a real NATS hub today would connect
cleanly and silently produce zero edges, forever. This is documented — not hidden — in
[ADR-0061](../decisions.md) and
[ADR-0220](../decisions.md)
(proposed, awaiting a reconciliation decision), and flagged in both affected commands'
`--help` output.

## Upgrade notes

All additive. New CLI commands (`nova lineage consume`) and flags
(`nova doctor --check-scheduler`); new optional `novaseal.yaml` field (`tsa_urls`,
defaults preserve existing single-TSA behavior); `bulk_insert_edges()`'s KuzuDB schema
changed (new `LineageNode` table) but this is a new write path with no prior production
data to migrate. No breaking changes, no new required dependencies.
