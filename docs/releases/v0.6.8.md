# v0.6.8 — Hot-path optimizations + honest benchmark re-interpretation

Released: 2026-05-09

The v0.6.7 benchmark surfaced what looked like a 10× ADR-0021 §6
budget violation. After profiling and adding an in-process
micro-benchmark that isolates orchestrator-only cost, the headline
finding **is actually the opposite**: the orchestrator's own work
is already within budget. The wall-clock overhead users see is
dominated by Python interpreter startup, not NovaFabric code.

This release ships three concrete orchestrator optimizations along
with the new measurement methodology.

## What's new

### Hot-path optimizations (orchestrator)

- **Lazy-import `jsonschema`** in `lineage/_importer.py`. The library
  was imported at module top to validate edge records, but added
  ~50 ms of import time even for captures with zero edges. Now it's
  imported inside `_validate_edge_record()`, which only fires when
  there's actually an edge to validate.
- **Skip OpenLineage event construction when no transport is
  configured.** New `is_configured()` env-var probe in
  `_ol_transport.py`; the orchestrator's START / COMPLETE event
  builders are only invoked when at least one of `OPENLINEAGE_URL` /
  `OPENLINEAGE_FILE` is set. Saves ~10–20 ms when neither is set
  (the common case).
- **Parallelize env-lock capture with the subprocess.**
  `capture_environment()` walks `importlib.metadata.distributions()`
  (~50 ms) and is independent of the workload. The orchestrator now
  runs it on a worker thread that overlaps with the subprocess's
  ~200 ms wall-clock — effectively hiding its cost for any workload
  longer than ~50 ms.

### New micro-benchmark

`benchmarks/orchestrator_microbench.py` measures only
`CaptureOrchestrator.run()` from inside an already-warm Python
process. This excludes the outer `nova` CLI startup so it isolates
the cost of NovaFabric's own per-capture work — which is what
orchestrator optimizations actually move.

```
orchestrator.run() in-process     median=  221.3 ms  stdev=  10.5 ms (n=30)
```

Of that 221 ms, **~200 ms is the inner Python subprocess** (interpreter
startup + sitecustomize hook-loader import + the workload itself).
NovaFabric's own non-subprocess work is therefore **~21 ms — already
within the ≤50 ms ADR-0021 §6 budget.**

### Honest re-interpretation of the v0.6.7 finding

The v0.6.7 release notes claimed `nova capture` exceeded the
`≤50 ms no-op budget by ~10×`. That over-attributed Python
interpreter startup to NovaFabric. After this release, the
`benchmarks/README.md` decomposes the wall-clock measurement
honestly:

- ~250 ms — outer `nova` CLI startup (Python + typer + rich +
  project imports)
- ~200 ms — inner subprocess Python startup + sitecustomize loader
- ~21 ms — orchestrator's own work (within budget)
- ~10–50 ms — variance band

To reduce wall-clock further requires architectural changes beyond
the orchestrator (lighter sitecustomize loader, in-process capture
mode, lazy CLI subcommand imports). Those are queued for v0.7.x;
they are explicitly listed in `benchmarks/README.md` so any future
contributor knows the path forward.

## Quality

- **667 tests passing** (unchanged from v0.6.7 — no functional

None. All changes are internal optimizations + new measurement
tooling. The capsule format, CLI surface, and behavior are unchanged.
