# v0.13.0 — Maker-Checker Dual-Approval for Asset Promotion

Released: 2026-05-15

Asset promotions to `staging` or `production` can now require two cryptographically
distinct identities: a **proposer** (maker) and an **approver** (checker). The
`nova promote` command is restructured as a sub-group. Opt-in via
`maker_checker_gate.rego`.

---

## Background

ADR-0058 formalizes the maker-checker dual-approval pattern for the NovaFabric
asset promotion flow. ADR-0018 is amended with two new RBAC roles: `promoter`
(maker) and `approver` (checker).

The design goal is Separation of Duties (SoD) enforced at the cryptographic level:
the approver's Ed25519 key fingerprint must differ from the proposer's, and both
identities must differ as named strings. Neither policy nor runtime configuration
can override this constraint — it is enforced by the promotion service before
the database write.

---

## Breaking Change

`nova promote <name@version> --to <status>` is renamed to
`nova promote direct <name@version> --to <status>`.

The `promote` command is now a sub-group. Old scripts referencing `nova promote`
must add `direct` as the first positional argument. There is no deprecation period
— the old invocation exits with an error starting in v0.13.0.

## Added

### `nova promote direct <name@version> --to <status> [--force]`

Drop-in replacement for the old `nova promote`. Single-actor; no SoD enforcement.

### `nova promote propose <name@version> --to <status> [--identity NAME]`

Opens a maker-checker proposal. The command:

1. Calls `ensure_keypair(identity)` — auto-generates an Ed25519 key at
   `~/.config/novafabric/keyring/<identity>.pem` if one does not exist.
2. Constructs the canonical payload:
   `SHA-256(proposal_id + "|" + name + "@" + version + ":" + to_status)`.
3. Signs the payload with the proposer's private key.
4. Writes a row to the `promotion_proposals` SQLite table.
5. Prints the proposal ID.

### `nova promote approve <name@version> [--identity NAME]`

Approves the latest open proposal for the named asset. The command:

1. Looks up the open proposal for `name@version`.
2. Re-derives the canonical payload and verifies the proposer's signature.
3. Verifies the approver's key fingerprint differs from the proposer's.
4. Verifies the approver's identity string differs from the proposer's.
5. Signs the approval payload.
6. Calls `promote_asset()` — the same path as `nova promote direct`.
7. Audit-logs both `promote.propose` and `promote.approve` events.

### `src/novafabric/trust/keyring.py`

New module — Ed25519 keypair management:

- `ensure_keypair(identity)` — load or generate; PEM stored at
  `~/.config/novafabric/keyring/<identity>.pem`.
- `sign_payload(key, payload)` — Ed25519 sign; base64url encoded.
- `verify_sig(pubkey, sig_b64, payload)` — verify; raises `ValueError` on failure.
- `canonical_payload(proposal_id, name, version, to_status)` — deterministic bytes.

### `promotion_proposals` table (registry SQLite)

Appended to `init_schema()` in `store.py`. Columns: `proposal_id`, `asset_name`,
`asset_version`, `to_status`, `proposer`, `proposer_key_fp`, `proposer_sig`,
`proposed_at`, `state`, `approver`, `approver_key_fp`, `approver_sig`, `approved_at`.

### `registry.service.SoDViolationError`

Raised by `approve_promotion()` when:
- `approver_key_fp == proposer_key_fp` → "SoD violation: same keypair"
- `approver == proposer` → "SoD violation: same identity"

### `src/novafabric/policies/novafabric/defaults/maker_checker_gate.rego`

Opt-in Rego gate — when loaded, blocks `promote_direct` to `staging` or
`production`. Works with the existing OPA engine; requires no server restart.

### `tests/test_sod_promote.py`

14 new tests covering: keyring round-trip, canonical payload stability,
`propose_promotion` service, `approve_promotion` happy path, SoD violation
(same keypair), SoD violation (same identity), audit trail, and CLI integration.

## Upgrade Notes

If you have scripts or CI jobs using `nova promote <ref> --to <status>`, add
`direct` as the first positional argument:

```bash
# v0.12 and earlier
nova promote fraud-model@1.0.0 --to staging

# v0.13.0+
nova promote direct fraud-model@1.0.0 --to staging
```

The maker-checker flow is opt-in. If you do not load `maker_checker_gate.rego`,
`nova promote direct` behaves identically to the old `nova promote`.
