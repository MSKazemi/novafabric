# NovaFabric v0.99.0 — 2026-08-05

**`pip install novafabric` drops from 412 MB to 113 MB.** NovaFabric's pitch is
local-first — install it, capture a run, replay it, no server and no cluster.
The install did not match the pitch: a default install pulled 412 MB across 50
packages, most of it for infrastructure a default user could never reach. This
release fixes that, and it is the one change in the packaging-hardening program
that needs an ADR, because it changes what is importable after a plain install.

## Also in this release: four defects a source-tree test run could not see

The packaging work below is the headline, but this release also carries four
correctness fixes. Three were **live on every released install** — and all three
were invisible to the test suite, because the suite runs from the source tree
where repo-root fallbacks resolve and hooks never contend.

### Three schema validators were never in the wheel

`novafabric.envelope.validator`, `novafabric.import_blob.service` and
`novafabric.capsule.validator` each loaded their JSON Schema from the repo-root
`schemas/` directory, which does not ship. On a plain `pip install novafabric`,
Event Envelope v1 validation and parent/child capsule validation raised
`FileNotFoundError`, and batch-import manifest validation resolved a path
outside `site-packages`.

Fixed by mapping the canonical files into the package at build time
(`force-include`) and making each loader prefer the packaged path — deliberately
**not** by copying them under `src/`, which would recreate the two-schema-trees
problem. Verified by building the wheel and exercising all three in a clean
virtualenv, before and after.

### ~1.5% of API keys could never be rotated or revoked

`key_id` came from `secrets.token_urlsafe`, whose alphabet includes `-`, so
1 in 65 ids (1.54%, measured over 200,000 draws) began with a hyphen — and every
`nova server api-key` command takes the id as a *positional* argument, so Click
parsed it as an option and exited 2. New ids are re-drawn until the first
character is alphanumeric. **Keys issued before this fix still work**: pass the
id after a trailing `--`, e.g.
`nova server api-key rotate --db-path k.db -- -Jabc123`.

### Concurrent in-process captures corrupted each other

`capture.hooks` keeps one module-level hook list and one `EventRecorder`, and
eight of the nine in-process call sites drove them unguarded. Two overlapping
captures meant the second inherited the first's recorder (**events filed into
the wrong capsule**), stacked a second patch layer, and whichever finished first
tore down both. ADR-0224 adds an ownership token, and every adapter now records
`metadata.wire_capture` as `installed`, `installed-contended` or
`skipped-concurrent` — so a short stream can never be misread as "nothing
happened". Full per-task isolation is phase 2, specified and not yet built.

### Nine schema `$id` collisions

Nine schema pairs declared the same `$id` while disagreeing about what they
accept; measured, the canonical Run Capsule schema *rejected* a capsule
`nova capture` had just written. Canonical OAS v1 **target** schemas are now
identified `.../<name>-v1.schema.json` and say in `$comment` that they are not
yet in force. **No producer or capsule changes** — ADR-0034 §1 keeps the spec in
pre-freeze draft, so `^1\.` is a target, not a contract.

### ADR-0024's license policy is enforced, not just written

`scripts/license_gate.py` + `.license-policy.toml` resolve every installed
distribution's license and block on policy, closing a gap the ADR had admitted
for fifteen months. It runs on push, PR, and **weekly** — an upstream relicense
changes nothing in `uv.lock` but everything for the policy. Disjunction-aware
(a tri-licensed package resolves to its most permissive arm), and Tier D is
forbidden outright.

## Highlights

### ADR-0222: four dependencies move from core to extras

`duckdb`, `pyarrow`, `python-louvain` and `clickhouse-connect` are no longer
unconditional dependencies. Every one of their import sites was *already* behind
an extra — `evidence_fabric/*` (the `scale` tier), `serve/topology/*` (the
opt-in dashboard), `lineage/migration/*`, and `cost/clickhouse_store.py` — so a
default install was paying for all four and never able to use them.
`python-louvain` was also the only path `numpy` had into a bare install: a
16.7 MB scientific-computing stack, for a community-detection pass in an
experimental dashboard you had not installed. And `clickhouse-connect` was
pinned twice, in both core and the `scale` extra, with two version floors free
to drift apart.

Measured into a genuinely clean venv, not projected:

| | site-packages | packages |
|---|---|---|
| v0.95.0 | 412 MB | 50 |
| v0.99.0 | **~113 MB** | **40** |
| delta | **−299 MB (−72.6 %)** | −10 |

Also dropped, transitively: `numpy`, `lz4`, `backports.zstd`, `urllib3`.

> **Two notes on these numbers, so they are not read as more precise than they
> are.** The package count moved from 42 to 40 after this release note was first
> written: closing ADR-0222 OQ-2 also took `pyjwt` and `python-multipart` out of
> core (both are server-only). That is ~300 KB, so it does not move the MB
> figure.
>
> The MB column is method-sensitive and should be read as approximate. An
> independent re-measure on 2026-08-01 (`python -m venv` + `pip install .`) read
> **116 MB** for the whole venv and **100 MB** excluding pip/setuptools, against
> the 113 MB recorded here. The 3 MB spread is not explained, and the two
> measurements were not taken the same way — so treat −72.6 % as the honest
> order of the win, not a figure to quote to three significant digits. The
> package counts, which are exact and reproducible, are the more reliable half
> of this table.

### `networkx` deliberately stays

It is the obvious fifth candidate and it is staying, for a reason worth knowing:
networkx is imported eagerly at CLI start-up (`cli/main.py` → `cli/insights.py`
→ `lineage/analytics/`), so moving it would break `nova --help` itself. It also
backs the default `nova insights` and `nova lineage` commands.

Note the distinction that makes this safe: `nova insights` uses networkx's own
pure-Python `nx.community.louvain_communities`. The separate `python-louvain`
distribution (`import community`) is used only by the dashboard's topology
extractor — that is the one that moved. Conflating them would have broken
`nova insights`.

### The degradation contract

Moving a dependency is only safe if every core-reachable use of it behaves
sensibly without it. v0.99.0 adopts an explicit contract:

> Either fall back to a stdlib-equivalent path producing **identical** results,
> or raise an `ImportError` naming the **exact extra** to install. Never a silent
> wrong answer.

| What you run | Without the extra |
|---|---|
| `nova query` | Falls back to stdlib `sqlite3`, identical rows, reports `index.engine: "sqlite"` |
| `nova backup` | Skips the derived DuckDB topology cache with a stated reason; the backup still succeeds |
| `nova restore` | **Fails loudly** — but only if a `.duckdb` member is actually in the archive. Unverified is not verified |
| `nova insights` | Report still builds; notes the ignored cost source |
| ClickHouse accumulator / cost store | `ImportError: ... pip install novafabric[clickhouse]` |
| `evidence_fabric.DuckDBAccumulator` | `ImportError: ... pip install novafabric[scale]` |

Backup and restore land on opposite sides on purpose: skipping a rebuildable
cache during backup loses no evidence, whereas calling a restore verified when
the store was never opened would be exactly the silent wrong answer the contract
forbids.

This is enforced by tests, not prose — including a parity test that runs the
DuckDB and SQLite query engines over the same capsules across five query shapes
and asserts the rows are equal. Without that, the new `[query]` extra would be a
correctness dependency rather than a performance one.

> **`[query]` is not currently an accelerator.** ADR-0222 left the DuckDB-vs-SQLite
> crossover unmeasured. Measuring it (ADR-0222 OQ-3,
> `bench/query/MEASURED_CEILING.md`) found no crossover: DuckDB is ~20× *slower*
> at every directory size from 10 to 20,000 capsules, because the index build
> inserts row by row rather than using DuckDB's bulk appender. Selecting DuckDB
> implicitly therefore made `nova query` slower for anyone who installed
> `[query]`, `[scale]` or `[all]`, so **SQLite is now the default engine
> regardless of what is installed**; `NOVAFABRIC_QUERY_ENGINE=duckdb` opts back
> in. Porting the index build to the appender API, after which this should be
> re-measured, is tracked separately.

### `evidence_fabric` imports lazily

`novafabric.evidence_fabric` used to import all six of its exports eagerly, so
*any* symbol — including the dependency-free `EventQueueConsumer` — required
duckdb and pyarrow. It now uses a PEP 562 `__getattr__`, so importing the
package pulls in nothing optional and resolving one backend never drags in
another's dependency. Its docstring also claimed `DuckDBAccumulator` and
`LocalPIITable` were "self-contained (no optional deps required)", which was
never true; that is corrected.

## Upgrading

> **Migration note.** If you relied on `duckdb`, `pyarrow`, `clickhouse_connect`
> or `community` (python-louvain) being importable after a plain
> `pip install novafabric`, install:
>
> ```bash
> pip install 'novafabric[all]'      # restores the previous install surface
> ```
>
> …or pick the narrower extra you actually need:
>
> | Extra | Provides |
> |---|---|
> | `novafabric[scale]` | duckdb, pyarrow, clickhouse-connect (+ the rest of the Evidence Fabric scale tier) |
> | `novafabric[serve]` | duckdb, pyarrow, python-louvain (+ FastAPI/uvicorn) |
> | `novafabric[query]` | duckdb — **new**. Gives `nova query` the DuckDB SQL surface, **not** speed: see the note below |
> | `novafabric[clickhouse]` | clickhouse-connect |
> | `novafabric[lineage-migration]` | pyarrow |
>
> These were never part of NovaFabric's public API, but they did work before, so
> it is called out as a break.

**Nothing else changes.** No capsule schema, evidence-bundle format, CLI flag or
REST endpoint change. `nova --help` and every default command behave identically
on a lean install — verified by running them in one.

**Docker and server deployments are unaffected.** `deploy/docker/Dockerfile`
installs `[server,serve,clickhouse,lineage-kuzu,lineage-migration]`, which
restores the full import surface inside the image. The `clickhouse` extra is new
there and load-bearing: without it the image would have silently lost cost
attribution and left the dashboard CostTab dead, since the compose `prod`
profile runs a ClickHouse container and sets `NOVA_CLICKHOUSE_URL`.

## Also fixed

- **The Docker image did not build at all.** Two missing `COPY` lines in the
  builder stage, both surfaced while verifying the container regression above:
  `alembic/` (required by `[tool.hatch.build.targets.wheel.force-include]`,
  broken since 2026-07-24) and `README.md` (required by the `readme` field added

- `cost/clickhouse_store` raised a bare
  `ModuleNotFoundError: No module named 'clickhouse_connect'` with no remedy. It

## Also in this release

ADR-0222 is the headline, but it shipped as one slice of a six-slice
packaging-hardening pass. The other five land under this same tag.

### PyPI metadata and four new narrow extras

`pyproject.toml`'s `[project]` table now carries `readme`, `authors`,
`keywords`, `classifiers` (Beta, Apache-2.0, Python 3.12-only to match the CI
matrix, Linux-only, `Typing :: Typed`) and `[project.urls]`
(Homepage/Documentation/Repository/Changelog/Issues), so the PyPI project page
renders real metadata instead of a near-blank one. `src/novafabric/py.typed`
(the PEP 561 marker) is now shipped in the wheel — **downstream type checkers
finally see NovaFabric's annotations**, which matches the project's own
`mypy strict = true` posture.

Four extras now actually exist and resolve: `novafabric[clickhouse]`,
`novafabric[nats]`, `novafabric[avro]` and `novafabric[energy-gpu]`. Shipped
code and shipped docs had been telling people to install them for months. Those
hints — in
`evidence_fabric/clickhouse_accumulator.py`, `evidence_fabric/nats_consumer.py`,
`evidence_fabric/avro_serializer.py`, and the `[energy-gpu]` instructions
published back in the v0.55.0/v0.56.0 notes — named extras that did not resolve.
`energy-gpu` depends on `nvidia-ml-py`, not the PyPI distribution literally
named `pynvml`, which is upstream-deprecated and no longer ships the `pynvml`
module the code imports.

`novafabric[all]` is also new: a self-referencing aggregate extra. It
deliberately excludes the cloud-vendor extras (`worm-s3`/`worm-azure`/`worm-gcs`,
`seal-aws`/`seal-azure`/`seal-gcp`) and the agent-framework adapter extras
(`openai-agents`, `google-adk`, `bedrock-agentcore`, `a2a`) — bundling every
cloud vendor and every competing agent framework would be dead weight for every
installer. Note it is a **superset** of the old default install, not an
equivalent: it restores importability, but it pulls `compliance`, `spkg`,
`scale`, `sigstore`, `janusgraph` and more besides, so it is larger than the
412 MB you had before. Prefer the narrow extra.

### Phantom-extra cleanup

Four install hints named an extra that never existed:

- `docs/developer-guide.md` told `NovaPySpool` users to
  `pip install novafabric[collector-cffi]`. There is no such extra and there
  cannot be one — `libnovaspool.so` is a Go shared library built out-of-band by
  a separate `go build`, not something `pyproject.toml` can express. The doc now
  says so, and documents the automatic pure-Python fallback when the `.so` is
  absent.
- The **dashboard's Eval tab** showed `pip install novafabric[eval]` on an empty
  suite list. The standard eval suites are core — registered via
  `[project.entry-points."novafabric.eval_suites"]`, never extra-gated — so the
  hint was simply false. Removed, and the dashboard bundle in
  `src/novafabric/serve/static/` was rebuilt, so the shipped UI no longer
  displays it.
- `design/spec/saml-sso-v0.md` (plus a fixture README and two JSON Schema
  `$comment`s) said `novafabric[server-saml]`; the real extra is
  `novafabric[saml]`.
- `design/spec/toolcall-schema-validation-v0.md` claimed the tool-call schema
  validator ships behind `novafabric[schema-validation]`. No such extra was ever
  added and none was needed — `jsonschema` is an unconditional core dependency.

`design/adr/` is immutable and untouched: ADR-0138 still literally says
`server-saml` and ADR-0128 still says `schema-validation`, now recorded as known,
permanently-allowed discrepancies between the historical decision record and the
shipped state. `tests/docs/test_extras_references.py` is the permanent guard —
it parses `[project.optional-dependencies]` and fails on any `novafabric[<name>]`
reference under `src/`, `docs/`, `web/` or `design/` (excluding the immutable
`docs/releases/` and `design/adr/`) that names a non-existent extra.

### Container image pins converged

An audit found five inconsistent `janusgraph/janusgraph` references — tests ran
`:latest`, the compose `prod` profile pinned `1.1.0`, the Helm chart pinned
`1.0.0`, docstrings agreed with neither — plus unpinned `:latest` on
`edoburu/pgbouncer` and `apache/age`. Everything now converges on
`janusgraph/janusgraph:1.1.0`, `edoburu/pgbouncer:v1.25.2-p0` and
`apache/age:release_PG16_1.6.0` (AGE tags follow `release_PG<major>_<version>`,
not semver; PG16 matches this project's Postgres baseline). `deploy/IMAGE_PINS.md`
documents each pin and `tests/deploy/test_image_pins.py` enforces it.

Two of these are behaviour changes, not just consistency fixes:

- **Helm chart users:** `deploy/helm/janusgraph/` `appVersion` and
  `image.tag` move **`1.0.0` → `1.1.0`**. A `helm upgrade` will roll your
  JanusGraph pods onto the newer image. Pin `image.tag` explicitly if you are
  not ready for that.
- **`nova lineage-store profile --image-tag`:** the default changes from
  `latest` to **unset**. Previously one `--image-tag` value was silently applied
  to three unrelated images, so `--target janusgraph-minimal` emitted
  `cassandra:latest` and `novafabric/novafabric:latest` regardless of the
  JanusGraph pin. Each image now carries its own independently-defaulted tag
  (`janusgraph_tag` defaults to `1.1.0`). `--image-tag` still works and still
  overrides all three, kept as a deprecated backward-compatible alias — no
  public break.

### Apache AGE compose profile — **experimental**

A dedicated `age` profile in `deploy/docker/docker-compose.yml` stands up a
standalone `apache/age:release_PG16_1.6.0` Postgres on `127.0.0.1:5433`, so
`AGELineageStore` can be exercised locally without testcontainers. It is
**opt-in and experimental**: not folded into `prod`, absent from the default
service set, and bound to loopback only.

```bash
make age-up      # EXPERIMENTAL: start ONLY the AGE lineage backend on :5433
make age-down    # stop and remove ONLY the age container
```

It is deliberately separate from the MetadataStore's `postgres` service on 5432
— the AGE extension is not in `postgres:16-alpine`, and the lineage graph is a
derived, rebuildable artifact that should not share the metadata database.
`AGELineageStore.__init__` self-initializes the extension and graph on connect,
so there is no init-SQL mount. DSN and the `[server]` extra requirement are
documented in `docs/developer-guide.md` and
`docs/ops/cluster-scale-migration.md`. `tests/deploy/test_compose_profiles.py`
asserts the profile stays opt-in and loopback-bound; the integration test that
stands up the real container is opt-in via
`NOVAFABRIC_RUN_DOCKER_COMPOSE_TESTS`.

### `deploy/pgbouncer/` removed

The repo carried two pgBouncer config directories. `deploy/pgbouncer/` was an
older, generic placeholder that nothing referenced; the canonical location is
`deploy/docker/{pgbouncer.ini,pgbouncer-userlist.txt,README-pgbouncer.md}`,
which is what the compose file and `docs/ops/cluster-scale-migration.md`
actually use and which already carried compose-matching values.

Every unique directive from the deleted template was ported forward first — a
commented-out read-replica `[databases]` stanza, the `max_client_conn` sizing
rule of thumb, `server_lifetime`/`log_pooler_errors`/`stats_period`, a
client-side TLS stanza, an admin-console access note, the
novafabric_app/novafabric_migrator role-split safety note (ADR-0040 §3), and the
RLS/`SET LOCAL` transaction-pooling rationale. The `pgbouncer_exporter`
monitoring section moved into `README-pgbouncer.md`. The deleted README's stale
quick-start (referencing the abandoned `bitnami/pgbouncer` image) was not
carried over.

## Try it

```bash
python3 -m venv /tmp/lean && /tmp/lean/bin/pip install novafabric==0.99.0
du -sh "$(/tmp/lean/bin/python -c 'import sysconfig;print(sysconfig.get_paths()["purelib"])')"

/tmp/lean/bin/nova --help                       # exits 0, no duckdb in sight
/tmp/lean/bin/nova query --select 'count()' --group-by model --since 30d --json
# -> "index": {"engine": "sqlite", ...}

/tmp/lean/bin/python -c "import duckdb"         # ModuleNotFoundError, as intended
/tmp/lean/bin/python -c "
import novafabric.evidence_fabric as ef
ef.EventQueueConsumer                            # fine — needs nothing optional
ef.DuckDBAccumulator                             # ImportError naming [scale]
"
```
